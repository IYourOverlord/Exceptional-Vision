# EV — математика производительности: холодный старт vs установившийся рендеринг

Дополнение к `ARCHITECTURE.md`. Раскладывает требование "быстро отрисовать огромные дистанции, а
дальнейший рендеринг сделать дешевле" на две разные инженерные задачи с разной математикой и разными
структурами данных под каждую.

## 0. Почему это две разные задачи

**Задача A — холодный старт.** Телепорт, spawn, `/tp`, резкий скачок render distance в настройках,
смена измерения. Узкое место — **throughput**: сколько секций/вокселей в секунду мы способны
воксилизировать, смешить и залить в GPU за единицу времени.

**Задача B — установившееся состояние.** Игрок стоит или идёт, данные уже построены. Узкое место —
**steady-state cost per frame**: сколько узлов дерева обходится, сколько draw call'ов, сколько памяти
трогается, сколько пересчитывается из-за движения камеры или правок мира.

Смешивать их в одну оптимизационную стратегию — типичная ошибка, из-за которой многие far-render моды
либо медленно стартуют, либо не удешевляют кадр после старта. Ниже — конкретика по каждой.

## Часть A: быстрый холодный старт на огромных дистанциях

### A.1 Приоритизация по углу обзора вместо построчного скана

Наивный скан секций `for x for z` даёт почти нулевую корреляцию с реальным полем зрения игрока —
тратим время на то, что за спиной, ещё до того, как построено то, что перед глазами.

```
priority(section) = angularDeviation(section, viewDir) * w1
                   + distance(section, camera) * w2
                   + (1 - lodLevel / maxLod) * w3
```

`angularDeviation` считается не через `acos` (дорогая трансцендентная функция), а как
`dot(normalize(toSection), viewDir)` — косинус угла, монотонно эквивалентный самому углу для целей
сортировки, но на порядок дешевле по вычислительной стоимости.

### A.2 Coarse-to-fine вместо fine-to-coarse

Стандартный паттерн (в т.ч. у прототипа, который анализировался ранее) — строить детальный LOD 0 и
агрегировать его вверх в грубые mip-уровни. Для холодного старта это неверно математически: чтобы
увидеть силуэт горы на 300+ блоках, LOD 0 не нужен вообще.

- Секция уровня `L` имеет размер `32 * 2^L` блоков (при `MAX_LOD_LEVEL = 6` — до 2048 блоков).
- Грубый воксель на дальнем LOD строится прямо из heightmap чанка и доминирующего биома в квадранте,
  без чтения отдельных блоков: `O(1)` на воксель вместо `O(32³)`.
- На LOD 4+ точность до блока визуально неотличима — экранная погрешность меньше пикселя (см. A.3).

Результат: за первые ~200 мс после телепорта уже виден грубый силуэт всего горизонта, детализация
подгружается постепенно поверх него — вместо пустого экрана, пока строится всё по порядку.

### A.3 Screen-space error metric вместо фиксированных дистанционных порогов

```
projectedError(voxelSize, distance, fovY, screenHeightPx) =
    (voxelSize / distance) * (screenHeightPx / (2 * tan(fovY / 2)))
```

LOD выбирается как минимальный уровень `L`, при котором `projectedError <= errorThresholdPx`
(обычно 1.5–2 px). Преимущества:

- на большом разрешении/широком FOV автоматически подтягивается более точный LOD;
- на узком FOV (zoom) экономим ресурсы там, где разница всё равно не видна;
- LOD-переходы при движении камеры получаются плавными, без резких "попингов" по фиксированным ступеням.

`screenHeightPx / (2*tan(fovY/2))` — константа для текущего кадра (`projectionScale`), пересчитывается
раз в кадр (при ресайзе/смене FOV), а не для каждой секции — тысячи вызовов `tan()` в кадр заменяются
на одно умножение/деление на секцию.

### A.4 Sharded work-stealing bucket queue вместо единой приоритетной кучи

Единая `PriorityBlockingQueue` на все воркер-потоки под холодным стартом становится узким местом:
`O(log n)` вставка на общей блокируемой куче, contention растёт быстрее числа ядер.

Решение:
- приоритет квантуется в фиксированное число дискретных корзин (например, 64);
- у каждого воркер-потока — собственный массив из 64 lock-free deque (Chase-Lev deque);
- свои задачи поток кладёт в свой конец без синхронизации (`pushBottom`);
- простаивающие воркеры воруют работу из чужого `popTop` (lock-free CAS), начиная с высокоприоритетных корзин.

```java
final class ShardedPriorityQueue {
    private final ChaseLevDeque[][] bucketsPerWorker; // [workerId][bucketIndex]
    private static final int BUCKET_COUNT = 64;

    void submit(int workerHint, long priority, MeshTask task) {
        int bucket = (int) (priority >>> (64 - 6));
        bucketsPerWorker[workerHint][bucket].pushBottom(task);
    }

    MeshTask poll(int workerId) {
        for (int b = 0; b < BUCKET_COUNT; b++) {
            MeshTask t = bucketsPerWorker[workerId][b].popBottom();
            if (t != null) return t;
        }
        return stealFromOthers(workerId);
    }
}
```

Вставка/извлечение — `O(1)` амортизированно вместо `O(log n)`, без глобальной блокировки. На холодном
старте с сотнями тысяч задач это прямой линейный выигрыш по CPU-времени, потраченному только на
поддержание очереди — до учёта самой работы мешинга.

### A.5 SIMD через Vector API (JEP 448, `jdk.incubator.vector`) для плотных числовых циклов

NeoForge 1.21.1 требует Java 21, где Vector API доступен как incubator-модуль — реальная
SIMD-векторизация из чистого Java, без JNI.

```java
import jdk.incubator.vector.*;

final class SimdMipGen {
    private static final VectorSpecies<Integer> SPECIES = IntVector.SPECIES_PREFERRED;

    void mipDown(int[] childPalette, int[] parentPalette, int parentCount) {
        int upperBound = SPECIES.loopBound(parentCount);
        int i = 0;
        for (; i < upperBound; i += SPECIES.length()) {
            var a = IntVector.fromArray(SPECIES, childPalette, i * 8);
            var b = IntVector.fromArray(SPECIES, childPalette, i * 8 + SPECIES.length());
            var mask = a.eq(b);
            a.blend(b, mask.not()).intoArray(parentPalette, i);
        }
        for (; i < parentCount; i++) {
            parentPalette[i] = scalarMajorityVote(childPalette, i);
        }
    }
}
```

`SPECIES_PREFERRED` сам выбирает оптимальную ширину под доступное железо (SSE/AVX2/AVX-512-эквивалент).
На плотных числовых циклах агрегации/вокселизации это обычно даёт кратный (4–8x) выигрыш по throughput
именно в момент, когда за секунды нужно обработать сотни тысяч узлов.

Второе применение Vector API — batch frustum/AABB тесты на CPU-стороне (до отправки батча на GPU):
вместо скалярной проверки каждой bounding box по отдельности, проверяем `SPECIES.length()` боксов
за одну векторную операцию сравнения с плоскостями frustum.

### A.6 Батчинг GPU upload вместо множества мелких вызовов

```
cost(N мелких upload) ≈ N * (driver_call_overhead + memcpy_cost)
cost(1 батч-upload)   ≈ 1 * driver_call_overhead + N * memcpy_cost
```

Готовые мешлеты копятся в CPU-side staging-буфере (persistent mapped) и заливаются одним проходом раз
в кадр, а не раз в готовую секцию. Экономия — на количестве вызовов драйверу (порядка микросекунд
каждый), которых на холодном старте могут быть тысячи в первые кадры.

## Часть B: дешёвый установившийся рендеринг

### B.1 Persistent-kernel traversal — фундамент дешёвого steady-state

Один compute dispatch запускает N персистентных workgroup, которые сами вычитывают работу из
atomic-очереди (SSBO-кольцо) и сами добавляют туда дочерние узлы (self-feeding queue), вместо
последовательных dispatch+barrier по каждому уровню дерева. Устраняет `O(глубина дерева)`
CPU-GPU синхронизаций каждый кадр — включая кадры, где дерево вообще не менялось.

### B.2 Temporal reprojection: инкрементальный re-traversal

Между соседними кадрами камера обычно поворачивается на доли градуса. Вместо обхода всего дерева
заново:

1. **Re-verify pass** — берём working set узлов, видимых в прошлом кадре (хранится в персистентном
   GPU-буфере), и повторно проверяем occlusion/frustum только для них. Набор уже мал.
2. **Delta pass** — обходим только те top-level поддеревья, чей bounding volume попадает в разницу
   между frustum текущего и предыдущего кадра (новая геометрия, вошедшая в обзор при повороте).
3. Полный traversal с нуля — только при разрыве когерентности (телепорт, резкий рывок камеры,
   смена измерения), детектируется по `cameraDelta > thresholdDegrees` за кадр.

```
наивно:            cost_per_frame = O(T),              T = размер всего дерева
temporal-coherent:  cost_per_frame = O(V + ΔV),         V = видимое множество, ΔV << T
```

При плавном движении (подавляющая часть игрового времени) это прямой, измеримый ответ на требование
"дальнейший рендеринг будет менее требовательным" — без потери качества, за счёт переиспользования
результата предыдущего кадра.

### B.3 Hi-Z occlusion тест — логарифмическая, а не линейная стоимость

```glsl
float mipLevel = max(0.0, ceil(log2(max(screenAABB.z - screenAABB.x, screenAABB.w - screenAABB.y))));
float occluderDepth = textureLod(hiZPyramid, screenAABB.center, mipLevel).r; // O(1) выборка
```

Один текстурный fetch на правильно выбранном mip-уровне Hi-Z пирамиды (аппаратный min-фильтр уже
агрегировал глубину по области) заменяет проход по каждому экранному пикселю bounding box. Стоимость
теста узла — `O(log(размер AABB в пикселях))`, а не `O(число пикселей)`.

### B.4 Structure-of-Arrays layout для горячих полей узла

Traversal на каждом шаге читает у узла 3 поля: bounds, occlusion-флаг, child-mask. Материалы и
streaming-состояние нужны реже (только на рендере / решениях о подгрузке). AoS-раскладка (все поля
узла подряд) тянет в кэш ненужные байты на каждый доступ.

```
buffer NodeBoundsSoA    { vec4 bounds[]; };       // читается каждым traversal-шагом
buffer NodeFlagsSoA     { uint flags[]; };        // читается каждым шагом
buffer NodeChildMaskSoA { uint childMask[]; };    // читается каждым шагом
buffer NodeMaterialSoA  { uint materialRef[]; };  // читается только при рендере
buffer NodeStreamSoA    { uint streamState[]; };  // читается только при streaming-решениях
```

SoA увеличивает долю полезных байт в каждой закешированной линии/транзакции памяти. Traversal —
типично memory-bound, а не compute-bound процесс, поэтому это напрямую снижает время кадра.

### B.5 GPU-driven indirect multi-draw

```
cost(N draw calls)          ≈ N * cpu_submit_overhead + N * gpu_state_change_cost
cost(1 indirect multi-draw) ≈ 1 * cpu_submit_overhead + N * gpu_vertex_processing_cost
```

Traversal-шейдер сам заполняет indirect-command буфер на GPU (offset/count/instance для каждой
видимой секции); CPU выполняет один `glMultiDrawElementsIndirectCount`, даже не зная точное число `N`
(оно читается GPU-драйвером из отдельного GPU-счётчика, который заполнил тот же traversal-проход).

### B.6 Dirty sub-region tracking при правке блоков

Секция делится на под-регионы (например, 8³ саб-региона внутри секции 32³). Изменение одного блока
помечает грязным только соответствующий саб-регион (и его соседей по границе — для корректного
пересчёта greedy-merge quad'ов на стыке), не всю секцию.

```
cost(правка блока) = O(саб-регион) вместо O(вся секция)
```

Это касается steady-state, а не холодного старта: именно во время устоявшегося игрового процесса
происходит редактирование мира.

## Практический эффект

- **Холодный старт**: время до "полностью читаемой" картины на огромной дистанции определяется не
  общим объёмом данных мира, а throughput конвейера A.1–A.6. Coarse-to-fine (A.2) даёт мгновенный
  грубый силуэт, остальные пункты ускоряют дозагрузку деталей поверх него.
- **Установившееся состояние**: стоимость кадра после того, как всё построено, определяется B.1–B.6
  и не растёт линейно с render distance — она растёт с размером **видимого + изменившегося** множества,
  а не всего мира. Это и есть формальный смысл "дальнейший рендеринг будет менее требовательным":
  не константная оптимизация, а асимптотика, отвязанная от полного объёма данных.
