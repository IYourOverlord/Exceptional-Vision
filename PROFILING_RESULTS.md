# PROFILING_RESULTS.md

Дата профилирования: 20 августа 2026, сессия 22:16:20–22:17:21 (JFR-запись `ev-coldstart.jfr`,
~62.3 сек wall-clock; таймер записи был установлен на `duration=120s`, но клиент был закрыт
раньше через выход из мира).

Тестовое окружение:
- GPU: NVIDIA GeForce RTX 4060 Ti (драйвер 610.88, GL 4.6.0)
- ОС: Windows 10 (amd64, version 10.0)
- JDK: Microsoft OpenJDK 64-Bit Server VM 21.0.10+7-LTS
- NeoForge: 21.1.235 (Minecraft 1.21.1, NeoForm 20240808.144430)
- Мод EV: ev-0.1.0-SNAPSHOT
- Размер/тип тестового мира: "New World", свежесгенерированный ванильной генерацией (не
  прегенерирован через Chunky), тестовый прогон длился ~38 секунд активной игры на спавне —
  ⚠ это НЕ удовлетворяет требованию тикета "большой мир с разнообразным рельефом" (Требования
  к реализации, п.1); мир только начал генерироваться вокруг спавна в момент записи, что прямо
  видно в самом профиле (56% CPU-сэмплов — vanilla world generation, не EV). Этот прогон
  профилирует **холодную генерацию чанков**, а не установившийся large-world сценарий, для
  которого создавался этот тикет. Результаты ниже валидны как первый диагностический срез, но
  чекпоинт следует повторить на прегенерированном/уже посещённом большом мире, чтобы получить
  показательную картину именно EV-подсистем без шума ванильной генерации.
- Конфиг EV на момент теста: `maxRenderDistanceBlocks: 4096`, `screenSpaceErrorThresholdPx: 1.5`,
  `workerThreadCount: 8`, `vramBudgetBytes: 0` — `enableDebugOverlay` статус не подтверждён из
  доступных логов
- Прочее: mixin-предупреждения о class version 65 vs JAVA_16 (безвредны, не связаны с EV)

## Инструменты, фактически использованные в этом прогоне

- **JFR** (`ev-coldstart.jfr`, `settings=profile`) — единственный источник чисел ниже.
  Проанализирован напрямую через `jdk.jfr.consumer` API (JMC недоступен в среде анализа).
- **GPU-side timing (RenderDoc / `/ev profile`)** — НЕ использован в этом прогоне. Ни одной
  GPU-таймингом метрики ниже нет — LWJGL/GL CPU-сэмплов в JFR практически нет (0.1% от всех
  `ExecutionSample`), а JFR не измеряет GPU-время само по себе. Все пункты, требующие GPU-side
  breakdown (draw call submission time, overdraw, memory bandwidth), помечены как TODO.
- **Ручной секундомер / визуальное наблюдение** — НЕ проводился отдельно в этом прогоне;
  Time-to-first-frame и Time-to-visually-complete ниже помечены TODO.
- **`/ev debug` overlay** — статус использования не подтверждён из доступных данных.

## Сценарий A — холодный старт

- Time-to-first-frame: **TODO** — не измерялось секундомером/видеозаписью в этом прогоне.
- Time-to-visually-complete: **TODO** — аналогично, не измерялось.
- Throughput секций/сек: **TODO** — в проанализированном JFR нет событий
  `MetricsRegistry.recordCounter`/`ImportStageStatus`; либо эти метрики не логируются на
  уровне, видимом JFR, либо тикеты 05/29 не эмитят их как JFR custom events. Не гадаю на
  основе косвенных чисел (например, числа сэмплов `meshFaceDirection`), это не то же самое,
  что реальный throughput.
- **Разбивка CPU-сэмплов по top-of-stack (fallback-метрика, не полная разбивка по стадиям
  storage/meshing/GPU-upload/render — но лучшее приближение, доступное из JFR CPU-сэмплирования
  в этом прогоне)**, из 5643 событий `jdk.ExecutionSample`:
  - **Vanilla world generation** (`net.minecraft.world.level.levelgen/biome/chunk/server.level`):
    **56.3%** (3178 сэмплов) — доминирует; это ожидаемо для свежего мира без прегенерации, но
    означает, что *этот конкретный прогон* не изолирует стоимость EV-подсистем от стоимости
    самой генерации мира.
  - **EV-код** (`dev.ev.*`, все модули совокупно): **7.7%** (436 сэмплов).
  - **JVM/GC/прочее** (не отнесено к вышеперечисленному, включая `FileSystemWatchService`,
    GC-фазы): **35.7%** (2014 сэмплов).
  - I/O (`sun.nio`, `java.io`, `java.util.zip`): 0.2% (12 сэмплов) — незначимо.
  - LWJGL/GL (`org.lwjgl.*`): 0.1% (3 сэмпла) — незначимо, GPU-сторона не покрыта этим методом
    измерения в принципе.
  - Storage I/O vs meshing vs GPU upload vs render (по методологии тикета) — **не разделено**;
    единственная EV-подсистема с достаточным числом сэмплов для внутренней разбивки — meshing
    (см. ниже), остальные (storage, GPU upload) не набрали значимого числа сэмплов отдельно от
    meshing в этом прогоне.

- **Внутри EV: единственный видимый в JFR meshing-поток** — `ev-mesh-worker` (127 сэмплов).
  Лог подтверждает старт 8 воркеров (`Started 8 EV meshing worker threads`), но в CPU-сэмплах
  JFR виден только один именованный так поток — вероятно, остальные 7 либо были простаивающими
  (мало работы за 38 секунд на спавне), либо используют другое имя потока, не содержащее
  `ev-mesh-worker` буквально. Не делаю предположений о причине без дополнительной проверки.
  Top-of-stack внутри этого потока:
  ```
  83  GreedyMeshStage.meshFaceDirection        (65.4% времени потока)
  7   OccupancySet.set
  5   InMemorySectionHandle.isEmpty
  5   GeometryChangeDeduplicator.hashQuads
  4   OccupancyStage.process
  3   MaterialBinStage.process
  ```
  `GreedyMeshStage.meshFaceDirection` доминирует — ожидаемо для greedy-meshing алгоритма
  (тикет 11), не является само по себе аномалией без сравнения с baseline/ожидаемым бюджетом.

признак из тикета не был подтверждён как присутствующий.

## Следующие шаги для полного закрытия чекпоинта

Этот прогон закрывает только часть требований тикета `P0-profiling-checkpoint.md`:
1. Требование "большой мир с разнообразным рельефом" (Требования к реализации, п.1) —
   **не выполнено**; нужен повторный прогон на прегенерированном/уже посещённом большом мире.
2. Time-to-first-frame / Time-to-visually-complete (Сценарий A) — нужен ручной секундомер или
   видеозапись при `/tp` на большую дистанцию.
3. Throughput секций/сек и разбивка по стадиям storage/meshing/GPU-upload/render (Сценарий A,
   п.3–4) — нужны реальные вызовы `MetricsRegistry.recordCounter`/`ImportStageStatus` в логах
   или отдельный источник этих данных; текущий JFR их не содержит.
4. Весь Сценарий B (frame time, CPU/GPU breakdown, draw call count, overdraw) — требует
   `/ev profile` (если реализован) или RenderDoc capture в игре на прогруженном большом мире,
   ни один не использовался в этом прогоне.
5. После получения п.1–4, таблицу "Решение по opt-тикетам" нужно пересмотреть — в частности,
   `16-opt`, `19-opt`, `20-opt`, `21-opt`, `22-opt`, `23-opt`, `25-opt`, `26-opt` сейчас не
   имеют реальных данных для решения "внедрять"/"пропустить" и остаются "отложить".

Критерий приёмки тикета п.2 ("все 10 строк заполнены не-шаблонным решением") формально
выполнен в том смысле, что каждая строка содержит конкретное обоснование, а не placeholder —
но фактическое покрытие метрик далеко от полного; 8 из 10 решений "отложить" отражают реальное
отсутствие данных, не леность измерения.
