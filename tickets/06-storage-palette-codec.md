# Тикет 06 — PaletteCodec (палитровое кодирование вокселей секции)

## Контекст
EV — мод дальней прорисовки для NeoForge 1.21.1. Модуль `ev-storage` (чистый Java,
без NeoForge/LWJGL — только JDK + fastutil), реализует персистентное воксельное хранилище.

Каждая секция — логически куб 32×32×32 = 32768 вокселей (см. тикет 01/02). Большинство
секций содержат мало уникальных материалов (воздух + 1-3 типа блока), особенно на дальних
LOD-уровнях, где секция агрегирует огромные объёмы мира в единый грубый воксель на область.
Хранить 32768 полных ID блоков (обычно 4 байта на blockstate) на секцию — расточительно.
Нужно палитровое кодирование: локальная палитра уникальных значений на секцию + компактный
массив индексов в палитру (число бит на индекс = `ceil(log2(paletteSize))`), плюс RLE-сжатие
поверх индексов для однородных областей (частый случай на грубых LOD).

## Готовый контракт из зависимостей (тикет 02, уже реализован)
```java
package dev.ev.api.storage;
public interface WorldSectionHandle {
    dev.ev.api.SectionPos position();
    int getVoxel(int localX, int localY, int localZ); // возвращает palette index, 0 = air/empty
    void setVoxel(int localX, int localY, int localZ, int paletteIndex);
    boolean isEmpty();
    WorldSectionHandle retain();
    void release();
    int refCount();
}
```

## Задача
Создать `dev.ev.storage.codec.PaletteCodec` — кодек, преобразующий сырой массив из
32768 int-значений (palette-относительные индексы, где сама глобальная палитра материалов
уже разрешена на более высоком уровне — этот класс работает только с уже-целыми индексами,
не знает о blockstate/Minecraft) в компактное бинарное представление и обратно.

### Формат кодирования (спроектируй сам на основе следующих требований, задокументируй в Javadoc класса)
1. Локальная палитра: список уникальных int-значений, встречающихся в секции, в порядке
   первого появления (encounter order). Индекс 0 в результирующей локальной палитре ДОЛЖЕН
   соответствовать значению 0 (воздух), даже если оно не последнее по частоте — зарезервируй
   это явно (см. п. 2 ниже про частый случай "вся секция — воздух").
2. Специальный быстрый путь: если вся секция состоит из одного-единственного значения
   (типично: полностью воздух, или полностью один материал на грубом LOD) — кодируй как
   4 байта заголовка + 4 байта значения, без всякого RLE/битовой упаковки. Это самый частый
   случай на дальних LOD-уровнях, оптимизируй именно под него.
3. Общий случай: битовая упаковка индексов в локальную палитру, `bitsPerIndex = max(1,
   ceil(log2(paletteSize)))`, индексы упакованы плотно (не байт-выровнено) в `long[]`
   аналогично тому, как Minecraft сам паковает `BlockState` в chunk section (можно опираться
   на этот общеизвестный паттерн, но не копируй код из Minecraft — реализуй самостоятельно).
4. Поверх битовой упаковки — RLE по Z-order (Morton order) обходу вокселей, а не по
   построчному XYZ-порядку: Z-order даёт лучшую пространственную локальность (соседние
   индексы в обходе физически близки в 3D), что увеличивает длину серий одинаковых значений
   для типичных "блочных" структур мира по сравнению с построчным обходом. Реализуй функции
   `mortonEncode3(x,y,z) -> int` и `mortonDecode3(morton) -> {x,y,z}` для 5-битных координат
   (0..31) каждая — используй классическую технику "bit interleaving" (magic numbers /
   sequential bit spreading), не наивный побитовый цикл, если это ощутимо медленнее (для
   диапазона 5 бит наивный цикл, вероятно, тоже приемлем — сравни, задокументируй выбор).
5. Формат заголовка должен включать однобайтовый тег кодека (`SINGLE_VALUE = 0`,
   `PALETTE_RLE = 1`), чтобы декодер понимал, какой путь использован — это готовит почву
   для будущих кодеков без изменения контракта (см. тикет 07, версионирование схемы).

### Публичный API
```java
package dev.ev.storage.codec;

public final class PaletteCodec {

    /** Encodes a raw 32x32x32 voxel grid (flat array, index = x + y*32 + z*32*32) into bytes. */
    public static byte[] encode(int[] voxelsFlat);

    /** Decodes bytes produced by encode() back into a flat 32x32x32 int array. */
    public static int[] decode(byte[] data);

    /** True if the given voxel array is a single repeated value (fast-path check before encode()). */
    public static boolean isUniform(int[] voxelsFlat);
}
```
(Внутренние вспомогательные классы/методы — Morton-кодирование, битовая упаковка/распаковка,
RLE — организуй по своему усмотрению в том же пакете `dev.ev.storage.codec`, но держи
файлы компактными: если `PaletteCodec` разрастается больше ~250 строк, вынеси
`MortonCode`, `BitPackedArray`, `RunLengthCodec` в отдельные файлы того же пакета.)

## Требования к реализации
1. `encode(int[])` принимает массив ровно 32768 элементов (`32*32*32`), бросает
   `IllegalArgumentException` при другом размере.
2. `decode(byte[])` должен для любого вывода `encode()` вернуть побитово идентичный исходный
   массив (round-trip корректность — это критично, любая потеря данных недопустима, кодек
   lossless).
3. Все int-значения voxelsFlat неотрицательны (палитровые индексы), максимум ожидаемо в
   пределах десятков тысяч уникальных материалов глобально, но локальная палитра одной
   секции обычно мала (единицы-десятки уникальных значений) — не оптимизируй специально под
   огромные локальные палитры, но не роняй корректность на них тоже.
4. Не используй Java-сериализацию (`ObjectOutputStream` и т.п.) — только ручная бинарная
   упаковка через `ByteBuffer`/`byte[]` вручную, для компактности и控制 формата.
5. Никаких зависимостей на NeoForge/LWJGL/Minecraft-классы.

## Юнит-тесты (обязательно, JUnit 5)
Создай `PaletteCodecTest`:
1. Round-trip: полностью однородный массив (все нули) → `encode` → `decode` → идентичен.
2. Round-trip: полностью однородный ненулевой массив.
3. Round-trip: случайный массив с 5-10 уникальными значениями, разным пространственным
   распределением (сгенерируй псевдослучайно с фиксированным seed для воспроизводимости).
4. Round-trip: "шахматный" паттерн (максимально плохой случай для RLE — почти нет длинных
   серий) — проверяет корректность, не только эффективность.
5. Round-trip: массив, где ровно 2 уникальных значения (проверка `bitsPerIndex = 1`).
6. `isUniform` корректно определяет однородность/неоднородность на нескольких кейсах.
7. `encode` бросает `IllegalArgumentException` на массиве неправильного размера.
8. `mortonEncode3`/`mortonDecode3` (если публичны или package-private, тестируй напрямую;
   если приватны — тестируй косвенно через round-trip кодека) — round-trip для всех 32768
   комбинаций координат 0..31, и хотя бы несколько конкретных известных значений вручную
   посчитанных для проверки правильности интерливинга битов.
9. Тест на компрессию (не строгая корректность, а sanity-check производительности формата):
   для полностью однородного массива `encode(...).length` должен быть **значительно** меньше
   `32768 * 4` байт (наивного представления) — например, менее 16 байт.

2. Все юнит-тесты проходят.
3. Модуль компилируется без ошибок и без зависимостей на NeoForge/LWJGL.
