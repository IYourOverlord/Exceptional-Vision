# Тикет 31-mvp — Финальная интеграция Волны 1 (MVP) и сквозной чеклист

## Контекст
EV реализуется в две волны (см. `MVP_INDEX.md`). Это интеграционный тикет ИМЕННО для
Волны 1 (MVP) — предполагается, что выполнены все MVP-тикеты (00-05, 06-07, 08-mvp, 09,
10-13, 14, 15-mvp, 17-18, 20-mvp, 21-mvp, 24, 26-mvp, 27-30, 32), но НИ ОДИН `*-opt` тикет
ещё не применён. Задача — сшить всё в рабочий, компилирующийся, реально функционирующий мод
(пусть и архитектурно простой), а затем перейти к `P0-profiling-checkpoint.md`, чтобы решить,
какие оптимизации из банка Волны 2 действительно нужны.

**Не путай с `31-integration-checklist-full.md`** — тот файл написан под предположение, что
opt-тикеты (persistent traversal, Hi-Z, indirect draw, sub-region dirty tracking) уже
применены, и ссылается на сущности, которых в MVP-архитектуре не существует. Если ты дошёл
до этого тикета сразу после Волны 1, не применяя ни одного opt-тикета — этот файл для тебя.

## Предварительное условие
Все MVP-тикеты (см. таблицу выше) должны быть выполнены — файлы существуют, каждый модуль
по отдельности компилируется и проходит свои юнит-тесты — до начала этого тикета.

## Задача — пошаговый чеклист

### Шаг 1 — Сборка всего проекта целиком
```
./gradlew build
```
Устрани ошибки компиляции от нестыковок между модулями. В MVP-архитектуре типичные источники
проще, чем в полной версии (нет GPU-side parent/child linkage, нет indirect draw geometry
lookup — эти сложности отложены в opt-тикеты), но всё равно жди:
- Различия в финальных сигнатурах контрактных классов между тем, что задокументировано в
  тикете, и тем, что реально реализовано.
- Несостыковки между `SimpleTraversal` (тикет `21-gpu-simple-traversal-mvp.md`) и тем, как
  `EVInstance.renderFarLod` (тикет 27) его вызывает — сверься с разделом "MVP-архитектура
  renderFarLod" в тикете 27, если что-то не сходится.
- `nodeId <-> geometry` связь для обычных (не indirect) draw calls — в MVP-версии это
  существенно проще, чем в opt (не нужен `NodeGeometryInfo` GPU-side буфер), но всё равно
  нужна какая-то связь "эта видимая `SectionPos` → где физически лежит её geometry в GPU
  буфере, чтобы вызвать draw" — финализируй эту схему здесь, если ни один предыдущий MVP-тикет
  явно её не установил (вероятный кандидат — простая Java-side `Map<SectionPos, GpuBuffer>`
  или аналог, так как в MVP нет необходимости в GPU-резидентной индексации).

### Шаг 2 — Оркестрация полного кадра (MVP-версия)
Создай (или используй уже созданный в тикете 27) класс, связывающий MVP-компоненты для
одного кадра:
```
FrustumTester (построен из view-projection матрицы текущего кадра) →
    SimpleTraversal.computeVisible(...) (тикет 21-mvp) →
    для каждой видимой SectionPos: обычный draw call через RenderBackend (тикет 04/18)
```
параллельно с независимым потоком:
```
DirtySectionTracker (тикет 26-mvp) → MeshTaskQueue (тикет 15-mvp) воркеры →
    GreedyMeshStage + MaterialBinStage + MeshletPackStage (тикеты 11-13) →
    GeometryChangeDeduplicator (тикет 26-mvp) → обычный GPU upload (не батчинг, тикет 17) →
    (следующий кадр видит обновлённую геометрию)
```
**Явно создай worker thread pool** (например, `ExecutorService` через
`Executors.newFixedThreadPool(config.workerThreadCount())`, где `config` —
`EVConfig`, тикет 28) — ни один из тикетов 11-15/26 не специфицирует явно, КТО
создаёт эти потоки и откуда берётся их число; это интеграционная ответственность именно
этого тикета. Каждый worker-поток в цикле вызывает `MeshTaskQueue.poll()` (блокирующий,
тикет 15-mvp), при получении задачи прогоняет её через `GreedyMeshStage`→...→
`GeometryChangeDeduplicator`, при `null` от `pollNonBlocking()`-подобной проверки на
shutdown корректно завершается. Задокументируй в `INTEGRATION_NOTES.md` (см. Шаг 6), где
именно в коде живёт этот пул (какой класс его создаёт/останавливает) — это первое, что
будущая сессия, ищущая "почему секции не мешатся", захочет найти.

Собери это в `EVInstance.renderFarLod` (тикет 27) через `FrameGraphBuilder` (тикет 24) —
даже в MVP-версии `FrameGraphBuilder` полезен для структуры кода, просто passes внутри него
проще (нет multi-stage GPU pipeline, который был бы после opt-тикетов).

### Шаг 3 — Storage → Meshing связка
Убедись, что путь `VoxelStorage.acquire` (тикет 02/08-mvp) → `WorldSectionHandle` →
`OccupancyStage` → `GreedyMeshStage` → ... → `MeshletBatch` реально протянут как один
конвейер, диспетчеризуемый через `MeshTaskQueue` (тикет 15-mvp) с приоритетом из
`MeshPriority.computeWithNearTierCheck(...)` (тикет 14 — НЕ голые `compute()` overload'ы,
именно `computeWithNearTierCheck`, который единственный включает двухъярусную near-player
проверку; тикет 14 явно предупреждает, что вызов "голых" overload'ов в обход этого метода
означает, что near-tier гарантия никогда не достигает реального кода — см. тот тикет за
подробностями). Реализуй (если ещё не существует явно) класс/метод, отвечающий за постановку
готовых-к-мешингу секций в `MeshTaskQueue` — вероятный кандидат: небольшой
`MeshSchedulingCoordinator` в `ev-render`, вызываемый раз в тик/кадр из
`EVInstance` (тикет 27), который для каждой известной, но ещё не смешенной секции
вычисляет приоритет через `computeWithNearTierCheck` (с текущей позицией камеры) и вызывает
`MeshTaskQueue.submit(...)`. Убедись, что `CoarseSectionGenerator` (тикет 09 — тоже не
разделён) реально используется для дальних LOD согласно решению `SectionGenerationPolicy`
(создай этот класс здесь, если ни один предыдущий тикет явно его не установил — решает для
данной `SectionPos` и `EVConfig` (тикет 28), полная вокселизация или coarse-путь).

### Шаг 4 — Реальные Minecraft-адаптеры
Идентично Шагу 4 из `31-integration-checklist-full.md` — этот шаг НЕ зависит от MVP/opt
разделения (адаптеры к реальным Minecraft-типам нужны в любом случае):
- `MinecraftHeightmapSource implements HeightmapSource` (тикет 09).
- `MinecraftMeshingContext implements MeshingContext` (тикет 03/11) — включая создание
  глобальной палитры `BlockState -> paletteIndex`, если она ещё не существует.
- Обработчик блочных изменений: подпишись на подходящее NeoForge block-change событие
  (уточни точное имя через web search) и вызови `DirtySectionTracker.markSectionDirty`
  (тикет 26-mvp — заметь, MVP-версия принимает целую `SectionPos`, не координаты локального
  вокселя, как это было бы у `DirtyRegionTracker.markBlockChanged` в opt-версии — определи
  `SectionPos` затронутой секции из world-space координат изменённого блока через
  `SectionPos.fromBlockCoord`, тикет 01).

### Шаг 5 — Сквозной запуск
Запусти мод в dev-окружении (`./gradlew :ev-neoforge:runClient` или актуальная задача),
зайди в тестовый мир, подтверди:
1. Мод загружается без исключений в логе.
2. `/ev debug` (тикет 29) выводит осмысленный снимок метрик, не падает.
3. Дальняя геометрия отрисовывается на экране за пределами обычной render distance ванильной
   игры (визуальная проверка) — даже в MVP-версии это должно работать, просто менее
   оптимально по frame time, чем после применения opt-тикетов.
4. При установке/разрушении блока рядом с игроком, геометрия обновляется — с задержкой,
   соответствующей полной пересборке секции (MVP не имеет sub-region granular обновления,
   это ожидаемо медленнее, чем было бы после `26-opt` — не считай это багом, если задержка
   заметна, но не критична; если задержка ЯВНО мешает играть — это входной сигнал для
   рассмотрения `26-opt` уже на этапе профилирования).
5. При телепорте (`/tp`) на большую дистанцию, грубый силуэт горизонта появляется быстро
   (проверка coarse-to-fine, тикет 09) — даже без GPU persistent traversal, приоритизация
   по углу обзора (тикет 14) на уровне порядка построения секций должна давать видимый эффект.
6. **Проверка совместимости с Sodium / Embeddium**:
   - При установке мода вместе с Sodium/Embeddium рендеринг ванильного мира и LOD-геометрии EV происходят без графических артефактов и миганий.
   - Сброс OpenGL состояния в `renderFarLod` предотвращает сбои шейдеров Sodium.
7. **Не ожидай** от MVP-версии: temporal coherence (frame time при неподвижной камере будет
   не ниже, чем при движении — это ожидаемо, не баг), occlusion culling (сцены с сильным
   перекрытием геометрии будут рендерить лишнее — тоже ожидаемо), низкое число draw calls на
   широком render distance (это будет много обычных draw calls, не один indirect — тоже
   ожидаемо). Явно НЕ проверяй эти пункты как критерии успеха этого тикета — они являются
   предметом `P0-profiling-checkpoint.md` и последующих opt-тикетов, не MVP.

### Шаг 6 — Устранение обнаруженных нестыковок
Задокументируй в файле `ev-neoforge/INTEGRATION_NOTES.md` (создай) любые расхождения
между тем, что предполагалось в отдельных MVP-тикетах, и тем, что реально потребовалось для
интеграции.

## Требования
1. Финальный собранный мод (`./gradlew :ev-neoforge:build`) не содержит
   `UnsupportedOperationException`-заглушек на путях кода, реально исполняемых при обычном
   игровом сценарии MVP-архитектуры.
2. Никакого нового мутируемого статического состояния введено в процессе интеграции.
3. `INTEGRATION_NOTES.md` создан и содержит содержательные записи.

## Критерии приёмки
1. `./gradlew build` — полная сборка всего проекта без ошибок.
2. `./gradlew test` — все юнит-тесты всех модулей проходят.
3. Мод реально запускается в dev-окружении без исключений при загрузке.
4. Все 6 пунктов из "Шаг 5 — Сквозной запуск" подтверждены вручную и задокументированы в
   `INTEGRATION_NOTES.md`, включая явное подтверждение пункта 6 (ожидаемые ограничения MVP
   зафиксированы как известные, не как найденные баги).
5. `ev-neoforge/INTEGRATION_NOTES.md` создан с содержательными записями.
6. `PROJECT_INDEX.md` (тикет 32) обновлён с общим статусом "Волна 1 (MVP) завершена,
   интегрирована, готова к профилированию" и явным списком, какая версия каждого
   разделённого на mvp/opt тикета сейчас активна (см. `MVP_INDEX.md` таблицу).
7. **Следующий шаг после этого тикета — `P0-profiling-checkpoint.md`, не какой-либо
   `*-opt` тикет напрямую.** Не пропускай профилирование, даже если кажется, что "и так
   понятно", что нужна такая-то оптимизация — см. обоснование в `MVP_INDEX.md`.
