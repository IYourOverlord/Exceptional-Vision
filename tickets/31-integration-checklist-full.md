# Тикет 31-integration-checklist-full — Интеграция ПОСЛЕ применения opt-тикетов

## 📌 Когда использовать этот файл, а не `31-integration-checklist-mvp.md`

Этот файл написан в предположении, что **все или почти все** `*-opt` тикеты Волны 2 (см.
`MVP_INDEX.md`) уже применены — он ссылается на `TraversalPass`, `HiZBuildPass`,
`IndirectCommandBuildPass`/`IndirectDrawPass`, `resolveChildNodeId` (GPU-side parent/child
linkage), `NodeGeometryInfo` (indirect draw geometry lookup), `DirtyRegionTracker` (sub-region
granular tracking) — все эти сущности существуют только если соответствующие opt-тикеты
(21-opt, 22-opt, 23-opt, 26-opt) были выполнены.

**Используй этот файл ТОЛЬКО после того, как хотя бы часть Волны 2 применена** (не
обязательно вся сразу — интеграция после каждого отдельного opt-тикета важнее, чем
дожидаться всех сразу, см. ниже "Промежуточная интеграция"). Если ты выполняешь этот тикет
сразу после Волны 1 (MVP), не применяя ни одного opt-тикета — используй
`31-integration-checklist-mvp.md` вместо этого файла, он написан именно под MVP-архитектуру
и не требует несуществующих ещё сущностей.

## ⚠️ Промежуточная интеграция после каждого отдельного opt-тикета

Не жди применения ВСЕХ выбранных по результатам `P0-profiling-checkpoint.md` opt-тикетов
перед тем, как прогонять интеграционный чеклист — применяй их по одному, каждый раз повторяя
сокращённую версию Шагов 1 и 5 ниже (полная сборка + сквозной запуск + новое профилирование
для подтверждения реального эффекта именно этого изменения). Это прямое следствие принципа
MVP-first: если внедрить сразу 3-4 opt-тикета, а потом профилировать — невозможно понять,
какой из них реально дал эффект, а какой оказался бесполезным или, хуже, взаимно
конфликтующим с другим. Полный чеклист ниже (все 6 шагов, включая `INTEGRATION_NOTES.md`)
имеет смысл прогонять целиком один раз — либо после первого opt-тикета (чтобы задать
паттерн), либо в конце, после того как все запланированные opt-тикеты применены по
отдельности с промежуточными сокращёнными проверками.

## Контекст
EV — мод дальней прорисовки для NeoForge 1.21.1. Все предыдущие 30 тикетов (00-30)
реализованы независимо, каждый в своём слое, с явными контрактами между слоями. Этот
финальный тикет — не про написание нового кода с нуля, а про **сшивание всех частей воедино**
в рабочий, компилирующийся, реально функционирующий мод, обнаружение и устранение нестыковок
между тикетами (которые неизбежны при параллельной/раздельной разработке разных частей
разными сессиями Клода), и валидацию сквозного пути данных: блок мира → воксельное хранилище
→ мешинг → GPU-буферы → traversal → рендер на экране.

## Предварительное условие
Все тикеты 00-30 должны быть выполнены (файлы существуют, каждый модуль по отдельности
компилируется и проходит свои юнит-тесты) до начала этого тикета. Если какие-то тикеты не
выполнены — этот тикет невыполним целиком; выполни недостающие сначала.

## Задача — пошаговый чеклист

### Шаг 1 — Сборка всего проекта целиком
```
./gradlew build
```
Устрани ЛЮБЫЕ ошибки компиляции, возникающие от нестыковок между модулями — типичные
источники, на которые стоит обратить внимание в первую очередь:
- Различия в финальных сигнатурах контрактных классов между тем, что задокументировано в
  тикете, и тем, что реально реализовано (например, если `TraversalDispatcher` из тикета 21
  получил другую сигнатуру метода `dispatch`, чем предполагал тикет 25 при написании
  `WorkQueueSeeder`-интеграции).
- Различия в точном имени/пакете биндинга между `node_buffers.glsl` (тикет 20) и тем, что
  ссылается `traversal.comp` (тикет 21) / `hiz_test.glsl` (тикет 22) / `build_indirect_commands.comp`
  (тикет 23) — все они должны использовать СОГЛАСОВАННЫЕ binding indices.
- `resolveChildNodeId` в `traversal.comp` (оставлен как заглушка/рабочее предположение в
  тикете 21) должен быть финализирован здесь согласно реальной схеме, установленной (или,
  если тикет 25 её не установил явно, установи её сейчас) для связи parent/child node id —
  это, вероятно, потребует добавления ещё одного SSBO (например, `ChildNodeIdsSoA`) в
  `node_buffers.glsl` или отдельный include-файл, с соответствующим Java-side управлением в
  `NodeBufferSoA` (тикет 20) или новом классе, если потребуется — это ожидаемая, легитимная
  работа для данного интеграционного тикета, не "провал" предыдущих тикетов.
- `nodeId <-> geometry offset/count` связь, аналогично упомянутая как открытый вопрос в
  тикете 23 (`NodeGeometryInfo` буфер) — финализируй конкретную схему здесь, свяжи её с
  тем, как `MeshletPackStage` (тикет 13) выдаёт готовую геометрию и как она реально
  загружается в общий vertex/index буфер через `StagingUploadRing` (тикет 19).

### Шаг 2 — Оркестрация полного кадра
Создай (если ещё не создан осмысленно в тикете 27) класс, реально связывающий все
`FramePass`-реализации (тикет 24) в правильном порядке для одного кадра:
```
HiZBuildPass (тикет 22) → TraversalPass (тикет 21, с temporal coordinator из тикета 25
    решающим FULL vs INCREMENTAL seeding) → IndirectCommandBuildPass (тикет 23, часть 1) →
    IndirectDrawPass (тикет 23, часть 2)
```
параллельно с независимым потоком:
```
DirtyRegionTracker (тикет 26) → MeshTaskQueue (тикет 15) воркеры → GreedyMeshStage +
    MaterialBinStage + MeshletPackStage (тикеты 11-13) → StagingUploadRing (тикет 19) →
    (следующий кадр видит обновлённую геометрию через NodeGeometryInfo)
```
**Явно создай worker thread pool** (например, `ExecutorService` через
`Executors.newFixedThreadPool(config.workerThreadCount())`, где `config` — `EVConfig`,
тикет 28), если это ещё не было сделано при выполнении `31-integration-checklist-mvp.md`
(если ты применяешь opt-тикеты ПОСЛЕ уже интегрированного MVP — этот пул уже должен
существовать, просто дополни/переиспользуй его, не создавай второй параллельный пул).
Задокументируй в `INTEGRATION_NOTES.md`, где именно живёт этот пул — та же ответственность,
что и в MVP-версии интеграции.

Собери это в `EVInstance.renderFarLod` (тикет 27) через `FrameGraphBuilder` (тикет 24),
с корректными `reads()`/`writes()` объявлениями для каждого pass, чтобы барьеры
расставились автоматически.

### Шаг 3 — Storage → Meshing связка
Убедись, что путь `VoxelStorage.acquire` (тикет 02/08) → `WorldSectionHandle` →
`OccupancyStage` → `GreedyMeshStage` → ... → `MeshletBatch` реально протянут как один
конвейер, диспетчеризуемый через `MeshTaskQueue` (тикет 15) с приоритетом из
`MeshPriority.computeWithNearTierCheck(...)` (тикет 14 — НЕ голые `compute()` overload'ы,
именно этот метод, единственный включающий двухъярусную near-player проверку). Если для
дальних LOD должен использоваться `CoarseSectionGenerator` (тикет 09) вместо полной
вокселизации — реализуй (если ещё не сделано ни в одном из предыдущих тикетов явно) политику
выбора: например, в классе `SectionGenerationPolicy`, решающем для данной `SectionPos` и
текущего `EVConfig` (тикет 28), какой генератор использовать (полная вокселизация из
реальных block-данных мира на ближних LOD, coarse
generator на дальних) — порог между "ближний/дальний" можно связать с
`ScreenSpaceErrorMetric.selectLodLevel` (тикет 14) или с отдельным сконфигурированным
порогом уровня LOD, выше которого используется coarse-путь.

### Шаг 4 — Реальные Minecraft-адаптеры
Несколько тикетов (03 `MeshingContext`, 09 `HeightmapSource`) намеренно оставили адаптацию
к реальным Minecraft/NeoForge типам (`ChunkAccess`, `BlockState`, `Heightmap`, `Biome`) вне
своего объёма, чтобы соответствующие модули (`ev-storage`, `ev-meshing`)
оставались чистыми от NeoForge-зависимостей. Реализуй эти адаптеры теперь, в
`ev-neoforge` (единственном модуле, которому разрешено видеть Minecraft-классы):
- `MinecraftHeightmapSource implements HeightmapSource` — оборачивает реальный
  `ChunkAccess`/`Heightmap`/`BiomeSource` доступ (используй web search, чтобы подтвердить
  актуальные NeoForge 1.21.1 API для доступа к heightmap/biome данных чанка, включая
  правильный способ получить доминирующий surface-материал как палитровый индекс,
  совместимый с тем, что использует остальная система).
- `MinecraftMeshingContext implements MeshingContext` — резолвит
  `getNeighborBoundaryVoxel`/`resolveMaterialId` через реальные соседние `WorldSectionHandle`
  и глобальную материал-палитру (нужно определить/создать глобальную палитру
  `BlockState -> paletteIndex`, если она ещё не существует ни в одном из предыдущих
  тикетов явно — это легитимная новая работа для интеграционного тикета, задокументируй
  созданную схему).
- Обработчик блочных изменений: подпишись на подходящее NeoForge block-change событие
  (уточни точное имя через web search — вероятно что-то в духе `BlockEvent.*` или
  наблюдение через существующие world-tick хуки) и вызови
  `DirtyRegionTracker.markBlockChanged` (тикет 26) соответствующим образом.

### Шаг 5 — Сквозной запуск
Запусти мод в dev-окружении (`./gradlew :ev-neoforge:runClient`, или актуальная задача
для NeoForge 1.21.1 dev-запуска — подтверди точное имя Gradle-задачи через
`./gradlew tasks` или документацию ModDevGradle, найденную web search в тикете 00),
зайди в тестовый мир, подтверди:
1. Мод загружается без исключений в логе.
2. `/ev debug` (тикет 29) выводит осмысленный снимок метрик, не падает.
3. Дальняя геометрия действительно отрисовывается на экране за пределами обычной
   render distance ванильной игры (визуальная проверка).
4. При движении камеры (не телепорте) FPS не деградирует линейно с render distance —
   косвенная проверка, что temporal coherence (тикет 25) реально работает, не откатывается
   молча на FULL traversal каждый кадр (можно добавить временный debug-лог,
   подтверждающий выбранный `TraversalMode` по кадрам, для этой конкретной проверки).
5. При установке/разрушении блока рядом с игроком, геометрия обновляется без задержки,
   заметно бросающейся в глаза, и без визуальных артефактов на границах секций.
6. При телепорте (`/tp`) на большую дистанцию, полный traversal срабатывает (не оставляет
   устаревший working set), и грубый силуэт горизонта появляется быстро (проверка coarse-
   to-fine, тикет 09, и приоритизации по углу обзора, тикет 14).

### Шаг 6 — Устранение обнаруженных нестыковок
Задокументируй в файле `ev-neoforge/INTEGRATION_NOTES.md` (создай этот файл) любые
расхождения между тем, что предполагалось в отдельных тикетах, и тем, что реально
потребовалось для интеграции — это ценная информация, если проект продолжит развиваться
дальнейшими тикетами (например, "тикет 21 предполагал X для resolveChildNodeId, но
реальная интеграция потребовала Y, потому что Z").

## Требования
1. Финальный собранный мод (`./gradlew :ev-neoforge:build`) не содержит
   `UnsupportedOperationException`-заглушек на путях кода, реально исполняемых при обычном
   игровом сценарии (заглушки, оставленные намеренно в отдельных тикетах для методов,
   которые дополняются позже — например, `GLRenderBackend.compilePipeline` до тикета 18 —
   должны быть все дополнены к этому моменту, раз все тикеты 00-30 предполагаются
   выполненными).
2. Никакого нового мутируемого статического состояния введено в процессе интеграции —
   тот же архитектурный принцип действует и здесь.
3. `INTEGRATION_NOTES.md` создан и содержит содержательные записи (не пустой файл, если
   хоть одна нестыковка была обнаружена и исправлена — а она почти наверняка будет, при
   такой degree of раздельной разработки).

## Критерии приёмки
1. `./gradlew build` — полная сборка всего проекта без ошибок.
2. `./gradlew test` — все юнит-тесты всех модулей проходят.
3. Мод реально запускается в dev-окружении (`runClient` или аналог) без исключений при
   загрузке.
4. Все 6 пунктов из "Шаг 5 — Сквозной запуск" подтверждены вручную и задокументированы
   (например, скриншотами или явным текстовым описанием результата каждой проверки) в
   `INTEGRATION_NOTES.md`.
5. `ev-neoforge/INTEGRATION_NOTES.md` создан с содержательными записями о любых
   расхождениях между тикетами, обнаруженных и исправленных в процессе интеграции.
