# Разметка тикетов по требуемому уровню модели (обновлено под MVP/opt разделение)

Три тира. Критерий не "объём кода", а: (а) сколько взаимосвязанных решений нужно держать
согласованными одновременно, (б) есть ли тонкая конкурентная/математическая логика, где
ошибка не видна при беглом чтении, (в) есть ли GPU/GLSL-специфика, непроверяемая без
реального железа "на глаз". Модель послабее обычно всё же выдаёт компилируемый код на любом
тикете — риск не в компиляции, а в тихих логических ошибках, которые всплывут только на
интеграционном тикете или, хуже, только на реальном плейтесте.

**Главный вывод после перехода на MVP-first план (см. `MVP_INDEX.md`): почти все
Tier-3-риски были сосредоточены в тикетах, которые теперь относятся к Волне 2 (`-opt`) и
не нужны в первом заходе вообще.** Если ты следуешь MVP-first плану — Opus-квота тебе
понадобится в первом заходе (Волна 1) существенно меньше, чем показывала исходная разметка.
Настоящий расход Opus-квоты сдвигается на момент, когда профилирование (`P0-profiling-checkpoint.md`)
реально укажет на конкретный `-opt` тикет — то есть по требованию, не заранее.

### Тир 2 — Sonnet справится хорошо, но стоит выборочно перепроверить

| Тикет | Где именно нужна аккуратность |
|---|---|
| `07-storage-schema-migration.md` | Дизайн формата — конкретные решения на выбор модели, не concurrency/GPU риск; ошибка не тихая, всплывёт на первом round-trip тесте. |
| `08-storage-section-cache-mvp.md` | Проще своей `-opt` пары (одна `ConcurrentHashMap`), но конкурентный тест всё равно важен — не совсем Tier 1. |
| `09-storage-heightmap-coarse-gen.md` | Не сложна алгоритмически, но легко скатывается в O(area) вместо O(1) на воксель, если не удержать инвариант через весь метод. Тест №6 в тикете специально ловит именно это. |
| `11-meshing-greedy-mesh-stage.md` | Алгоритм известный, но параметризация по 6 направлениям без дублирования кода 6 раз — источник off-by-one ошибок. Тест №5 (32×32 плоскость → 1 quad) — хороший лакмус. |
| `14-meshing-priority-function.md` | Формулы простые, но двухъярусный приоритет не должен численно пересекаться ни при каких значениях — вопрос дисциплины следования спецификации. |
| `15-meshing-priority-queue-mvp.md` | Тонкая обёртка вокруг встроенной JDK `PriorityBlockingQueue` — корректность самой структуры гарантирована JDK, риск только в обёртке. |
| `21-gpu-simple-traversal-mvp.md` | Простой CPU-side frustum test — стандартная, хорошо изученная геометрия, не GPU-специфичный риск. |
| `24-render-frame-graph.md` | Топологическая сортировка + обнаружение циклов — стандартные, хорошо изученные алгоритмы. |
| `26-render-dirty-tracking-mvp.md` | Простая бухгалтерская логика (Set секций + хэш-дедупликация) без конкурентности. |
| `31-integration-checklist-mvp.md` | Проще своей full-версии (меньше межтикетных нестыковок для разрешения — MVP-компоненты проще стыкуются), но по-прежнему требует держать в голове контракты многих тикетов сразу. |

### Тир 3 в Волне 1 — отсутствует

**Ни один MVP-тикет не отнесён к Tier 3.** Это прямое следствие MVP-first подхода: все
тикеты, содержавшие GPU work-stealing, lock-free конкурентность, persistent-mapped buffer
race conditions, Hi-Z проекционную математику — вынесены в Волну 2 и не нужны для первого
рабочего билда. Волна 1 целиком выполнима на Sonnet.

## Волна 2 (opt) — тиры (нужны ТОЛЬКО если `P0-profiling-checkpoint.md` укажет на конкретный тикет)

### Тир 3 — нужен Opus. Экономьте квоту именно на них, и только когда профилирование реально это подтвердит.

| Тикет | Почему именно здесь риск тихой ошибки максимален |
|---|---|
| `15-meshing-work-stealing-queue-opt.md` | Lock-free Chase-Lev deque на VarHandle/AtomicLongArray. Ошибка в happens-before гарантиях JVM memory model не даст исключения — даст редкую, невоспроизводимую потерю/дублирование задачи под нагрузкой. |
| `21-gpu-persistent-traversal-shader-opt.md` | Central architectural piece. Termination detection в persistent kernel — это ровно то, что сам Voxy (прототип) не осилил. Ошибка либо зависает GPU, либо тихо недообходит дерево, либо превращается в scalar-эквивалент без выигрыша — незаметно на маленьких тестовых сценах. |
| `19-gpu-upload-batching-opt.md` | Ring-buffer поверх persistent-mapped GPU-памяти с CPU-GPU race между перезаписью и незавершённым fence-чтением — ошибка даёт визуальную коррупцию геометрии, трудно воспроизводимый баг. |
| `22-gpu-hiz-occlusion-opt.md` | Математика проекции bounding sphere в screen-space + выбор mip-уровня + направление сравнения глубины (обычная vs reversed-Z). Ошибка тихая — либо culls видимое (pop-in баг), либо не culls ничего (тихая потеря производительности). |
| `25-render-temporal-reprojection-opt.md` | Решение "GPU-side working set vs CPU readback" — модель послабее выберет более простой (CPU-readback) путь без осознания, что это тихо убивает главный смысл тикета (устранение readback stall). |
| `26-render-dirty-subregion-opt.md` | Требует не только структуры учёта, но и НЕТРИВИАЛЬНОГО расширения уже существующего, протестированного `GreedyMeshStage` под partial-scope пересчёт — риск сломать существующую корректность полного пересчёта при добавлении нового режима. |
| `31-integration-checklist-full.md` | По определению требует одновременного удержания в голове контрактов всех применённых opt-тикетов и разрешения реальных нестыковок между ними (resolveChildNodeId, geometry offset scheme и т.д.). |

### Тир 2 — Sonnet справится, но с выборочной перепроверкой

| Тикет | Где именно нужна аккуратность |
|---|---|
| `08-storage-section-cache-opt.md` | Шардирование с bit-mixing — известный паттерн, конкурентный тест либо пройдёт, либо покажет проблему явно (не тихую). |
| `16-meshing-simd-mipgen-opt.md` | Векторизация — открытая инженерная задача, но с чёткими тестами против scalar reference; баг детерминирован и воспроизводим (не гонка). |
| `20-gpu-node-buffer-soa-opt.md` | Простая по сути структура (5 параллельных буферов), требует держать Java-side и GLSL-side layout согласованными — дисциплина, не глубокое reasoning. |
| `23-gpu-indirect-multidraw-opt.md` | Механика ясна (два прохода: build commands, потом draw), барьер между ними — единственная тонкость, явно расписанная в тикете с обоснованием. |

## Практическая рекомендация по распределению квоты

1. **Всю Волну 1 (23 MVP-тикета плюс инфраструктурные) — на Sonnet.** Ни один из них не
   требует Opus. Это уже даёт полностью рабочий, играбельный мод для реального
   профилирования.
2. **`P0-profiling-checkpoint.md` — тоже на Sonnet** (это чек-лист измерений и заполнение
   таблицы результатов, не требует глубокого reasoning, требует аккуратности сбора данных).
3. **Opus — только точечно, только для тех `-opt` тикетов, которые `P0-profiling-checkpoint.md`
   реально пометит как "внедрять".** Скорее всего, это будет 1-3 тикета из 6 Tier-3
   subsystem-опций Волны 2 (см. таблицу выше — не считая `31-integration-checklist-full.md`,
   который отдельная категория "переинтеграция", выполняется после каждого применённого
   opt-тикета, а не сам по себе один раз), не все 6 сразу — именно так и должен работать
   MVP-first подход: опровергать заранее предполагаемые узкие места измерением, а не тратить
   ресурс на все теоретически возможные оптимизации.
4. Если после профилирования выяснится, что нужен именно `21-gpu-persistent-traversal-shader-opt.md`
   (самый рискованный тикет всего плана) — рассмотри его выполнение вне Antigravity, если
   там нестабильные квоты (см. обсуждение в диалоге про лимиты Antigravity) — например, через
   прямой доступ к Claude Code или веб-интерфейс, перенося код вручную.
