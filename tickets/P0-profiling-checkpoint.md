# Тикет P0 — Профилирующий чекпоинт (обязателен перед Волной 2)

## Контекст
EV реализуется в две волны (см. `MVP_INDEX.md`): Волна 1 — простая, рабочая MVP-версия
каждой подсистемы; Волна 2 — банк точечных оптимизаций (`*-opt` тикеты), каждая из которых
устанавливается ТОЛЬКО если этот профилирующий чекпоинт покажет конкретный, соответствующий
ей диагностический признак. Это не формальность — весь смысл MVP-first подхода в том, чтобы
не тратить время и не вносить риск сложности туда, где измерение не подтверждает нужду.

**Предварительное условие**: Волна 1 (все MVP-тикеты, см. таблицу в `MVP_INDEX.md`) должна
быть полностью реализована, собрана, и мод должен реально запускаться в dev-окружении
(`runClient` или аналог) на реальном мире прежде, чем этот тикет имеет смысл выполнять —
профилирование неработающего/несобранного кода невозможно.

## Задача

### Часть 1 — что именно измерять

Раздели измерения на два независимых сценария (см. `PERFORMANCE_MATH.md`, если доступен в
контексте, за полным обоснованием, почему это разные задачи с разной математикой):

#### Сценарий A — холодный старт
Действие: телепорт (`/tp`) на большую дистанцию в непрогруженную область ЛИБО первый вход в
мир с большим `maxRenderDistanceBlocks` (см. `EVConfig`, тикет 28).

Метрики, которые нужно собрать:
1. **Time-to-first-frame** — сколько миллисекунд/секунд проходит от телепорта до момента,
   когда на экране появляется ЛЮБАЯ LOD-геометрия (не обязательно полная детализация).
2. **Time-to-visually-complete** — сколько времени проходит до момента, когда видимый
   горизонт выглядит "полным" (нет явно пустых/чёрных областей там, где должна быть
   геометрия) — субъективная оценка, но фиксируй конкретное время по наблюдению.
3. **Throughput секций/сек** — сколько секций реально обрабатывается (проходят весь путь
   storage→meshing→GPU upload) в секунду во время активного холодного старта — бери из
   `MetricsRegistry.recordCounter`/`ImportStageStatus` (тикеты 05/29), не гадай на глаз.
4. **Разбивка времени по стадиям** — из общего времени холодного старта, сколько потрачено
   на: (а) storage I/O (чтение/генерация воксельных данных), (б) meshing (occupancy+greedy
   mesh+material bin+meshlet pack), (в) GPU upload, (г) собственно рендер видимых уже
   загруженных секций. Это самая важная метрика этого сценария — она прямо говорит, какая
   стадия является узким местом холодного старта, то есть какие из `*-opt` тикетов,
   нацеленных на throughput (16-opt SIMD mip-агрегация, 19-opt батч-upload), имеют смысл.

#### Сценарий B — установившееся состояние (steady-state)
Действие: находясь в уже полностью прогруженной области, стой на месте 10+ секунд, затем
медленно двигайся/поворачивай камеру ещё 10+ секунд, затем резко разворачивайся (быстрый
поворот мышью) на несколько секунд.

Метрики:
1. **Frame time при неподвижной камере** — если traversal/culling выполняется каждый кадр
   безотносительно движения (MVP-версия делает именно так, см. `MVP_INDEX.md` — "Полный
   traversal каждый кадр" в Волне 1), эта метрика прямо покажет: составляет ли CPU-side
   traversal (тикет 21-mvp) заметную долю времени кадра ДАЖЕ когда камера не движется — если
   да, это прямой диагностический признак для `25-opt` (temporal reprojection).
2. **Frame time при плавном движении** vs **frame time при резком развороте** — сравнение
   покажет, насколько чувствителен frame time к объёму видимого множества, меняющегося за
   кадр — тоже входной сигнал для `25-opt`.
3. **CPU time vs GPU time breakdown за кадр** — раздельно замерь, сколько времени в кадре
   уходит на CPU-side traversal/culling (тикет 21-mvp, если ты реализовал его на CPU, как
   рекомендовано в MVP) и сколько — на собственно GPU-side рендер (draw calls, шейдеры).
   Если CPU-side доля доминирует — это входной сигнал для `21-opt` (перенос traversal на
   GPU через persistent-kernel). Если GPU-side доля доминирует и профиль показывает высокую
   memory bandwidth utilization — сигнал для `20-opt` (SoA layout).
4. **Draw call count и время, потраченное на них** — если MVP-версия (обычные draw calls на
   секцию, не indirect) показывает большое число видимых секций одновременно (типично для
   широкого render distance) — замерь, сколько времени именно на submission draw calls (не
   на сам рендеринг геометрии) — входной сигнал для `23-opt` (indirect multi-draw).
5. **Overdraw / GPU fragment shader cost в сценах с сильным взаимным перекрытием
   геометрии** (например, стоя в узкой долине между горами, или в плотной городской
   застройке, если применимо к контенту мира) — сигнал для `22-opt` (Hi-Z occlusion),
   отдельно от чистого frame time, так как occlusion экономит именно там, где
   перекрытие велико, а не универсально.
6. **Cache contention при высокой конкурентности** — во время холодного старта (много
   worker-потоков одновременно обращаются к `SectionCache`, тикет 08-mvp), замерь, сколько
   времени потоки суммарно проводят заблокированными на `ReentrantLock` кэша (через JFR, см.
   Часть 2) — если contention значительный, это сигнал для `08-opt` (шардирование). Аналогично
   для `PriorityBlockingQueue` (тикет 15-mvp) — contention на очереди — сигнал для `15-opt`.

### Часть 2 — какими инструментами измерять

1. **Java Flight Recorder (JFR)** — встроен в JDK, минимальный overhead, подходит для
   измерения CPU-side breakdown (storage I/O, meshing stages, lock contention, thread
   pool utilization). Запуск: `-XX:+FlightRecorder -XX:StartFlightRecording=duration=60s,
   filename=ev-coldstart.jfr` как JVM-аргумент dev-запуска (уточни точный способ
   передать JVM-аргументы в `runClient`-подобную Gradle-задачу NeoForge через web search,
   если не очевидно из `build.gradle.kts`). Анализируй `.jfr` через JDK Mission Control
   (JMC) — открытый инструмент от той же экосистемы, отдельная загрузка.
2. **GPU-side timing** — если `EVCommands`/`/ev profile <pass>` (тикет 29) к этому
   моменту реализован и функционален — используй его для per-pass GPU timing напрямую в
   игре. Если нет (тикет 29 в MVP мог оставить эту команду как частичный TODO, как было явно
   допущено в его тексте) — используй внешний GPU-профайлер: RenderDoc (бесплатный,
   кросс-платформенный, снимает единичный frame capture с полной разбивкой draw calls/
   GPU time per draw/shader occupancy) — подключение к Minecraft/LWJGL приложению стандартное
   через RenderDoc's "Launch Application" с указанием пути к Java + аргументами запуска;
   уточни актуальную процедуру через официальную документацию RenderDoc, если не уверен в
   деталях привязки к JVM-приложению конкретно.
3. **Встроенный debug overlay/команда** (`/ev debug`, тикет 29) — для быстрой, грубой
   ориентировки (queue depths, cache hit rate) без запуска внешних инструментов — используй
   как первый, самый дешёвый шаг перед тем, как доставать JFR/RenderDoc для более глубокого
   анализа.
4. **Простой ручной секундомер/визуальное наблюдение** для Time-to-first-frame/
   Time-to-visually-complete метрик Сценария A — эти метрики субъективны по своей природе
   (что значит "визуально полный горизонт"), точные профайлеры здесь не так полезны, как
   прямое наблюдение с записью экрана (для последующего покадрового разбора, если нужна
   точность до кадра).

внедрения других opt-тикетов" — не занимайся угадыванием.

## Требования к реализации
1. Профилирование должно проводиться на РЕАЛЬНОМ, не игрушечном тестовом мире — маленький
   плоский тестовый мир не выявит реальные узкие места (типичные для больших
   прегенерированных территорий, ради которых мод и существует). Используй достаточно
   большой мир (сгенерированный ванильно или прегенерированный, например через Chunky, если
   доступно) с разнообразным рельефом.
2. Профилируй с конфигом, близким к реалистичному пользовательскому сценарию (типичный
   `maxRenderDistanceBlocks`, не экстремальный тестовый максимум и не тривиальный минимум) —
   если конкретное число неочевидно, возьми что-то в диапазоне 2000-4000 блоков как разумный
   средний случай для мода дальней прорисовки.
3. Не пропускай сбор чисел "на глаз" — даже если что-то кажется очевидным ("конечно же CPU
   traversal — узкое место, это же O(nodeCount) каждый кадр") — запиши реальное измеренное
   число. Интуиция уже один раз привела к переусложнению без проверки (см. `MVP_INDEX.md`,
   мотивация всего этого документа) — не повторяй эту ошибку на этапе, специально созданном,
   чтобы её избежать.

## Критерии приёмки
1. `PROFILING_RESULTS.md` создан в корне репозитория с реальными, измеренными (не
   предполагаемыми) числами по обоим сценариям.
2. Все 10 строк таблицы "Решение по opt-тикетам" заполнены (не оставлены как `...`/`да / нет
   / неприменимо` шаблон) — для каждого из 10 `*-opt` тикетов есть явное решение (внедрять/
   пропустить/отложить) с конкретным обоснованием на основе собранных чисел, не общей фразой.
3. Раздел "Тестовое окружение" заполнен — GPU/драйвер/ОС/размер мира/конфиг — чтобы результаты
   были воспроизводимы и интерпретируемы (профиль на integrated GPU и на дискретной видеокарте
   даст качественно разные картины, это должно быть явно видно из контекста результатов).
4. `PROJECT_INDEX.md` (тикет 32) обновлён — секция "Известные архитектурные инварианты" или
   отдельная новая секция "Решения по opt-тикетам" отражает, какие `*-opt` тикеты были
   применены, а какие сознательно пропущены и почему — чтобы будущая сессия не пыталась
   бездумно "доделать" все opt-тикеты просто потому, что они существуют в репозитории тикетов.
