# Тикет 32 — PROJECT_INDEX.md: создание и ведение живой карты проекта

## Контекст
EV — мод дальней прорисовки для NeoForge 1.21.1, реализуемый по тикетам, разбитым на
две волны (см. `MVP_INDEX.md` — это главный навигатор, `INDEX.md` устарел, сохранён только
как справочник по исходной таблице контрактов): Волна 1 (MVP, простые версии подсистем) и
Волна 2 (`*-opt` тикеты, применяются по одному, только по результатам
`P0-profiling-checkpoint.md`). Каждый тикет, скорее всего, выполняется в ОТДЕЛЬНОЙ сессии
Клода без доступа к истории предыдущих сессий. `MVP_INDEX.md` даёт таблицу тикетов и их
зависимостей ДО начала работы — но не отражает, что реально получилось ПОСЛЕ выполнения
(финальные сигнатуры, если они отклонились от контракта тикета; реальные пути файлов;
однострочное назначение каждого класса; **какая версия — mvp или opt — сейчас реально
активна для каждой разделённой подсистемы**, что критично именно из-за двухволновой
структуры плана). Без этого каждая новая сессия вынуждена заново обходить дерево файлов
через `view`, чтобы понять текущее состояние кода — дорого по времени и токенам, особенно
ощутимо при работе с ограниченными квотами (см. `MODEL_ASSIGNMENT.md`).

Этот подход (живой, кратко обновляемый файл-справочник, отдельный от истории/прогресс-лога)
эмпирически доказал свою пользу в независимой более ранней попытке реализовать эту же
концепцию мода (`project-index/` из `IYourOverlord/Exceptional-Vision`) — там он оказался
основным способом быстро сориентироваться в проекте между сессиями, без необходимости
каждый раз читать все файлы заново. Этот тикет переносит ту же практику в EV.

## Задача

### Шаг 1 — создать `PROJECT_INDEX.md` в корне репозитория
Создай файл `PROJECT_INDEX.md` (корень репозитория, рядом с `INDEX.md` и
`ARCHITECTURE.md`/`PERFORMANCE_MATH.md`, если они физически присутствуют в репозитории — если
нет, не блокируйся на этом, просто создай `PROJECT_INDEX.md` независимо) со следующей
структурой (адаптируй под реальное состояние проекта на момент выполнения этого тикета —
если он выполняется РАНО, до большинства других тикетов, многие секции будут пустыми/
"не реализовано ещё", это нормально, файл создаётся один раз здесь, затем ВЕДЁТСЯ каждым
последующим тикетом, см. Шаг 2):

```markdown

Быстрый справочник по текущему состоянию кода. Читай это ПЕРЕД тем, как обходить файлы

Цель: NeoForge 1.21.1, Java 21, GPU-driven LOD far-render mod. См. ARCHITECTURE.md /

## 🌊 Статус MVP/opt волн (обязательная секция — критична именно для этого проекта)

Для каждой подсистемы, разделённой на mvp/opt версии (см. `MVP_INDEX.md`, таблица), укажи,
какая версия РЕАЛЬНО активна в коде прямо сейчас — это единственный надёжный способ для
новой сессии понять, ожидать ли ей увидеть `SectionCache` на `ConcurrentHashMap` или на
64 шардах, `SimpleTraversal` (CPU) или GPU persistent-kernel, и т.д., без построчного чтения
исходников.

```
| Подсистема | Активная версия | Тикет | Дата/повод перехода (если opt) |
|---|---|---|---|
| Кэш секций | MVP | 08-storage-section-cache-mvp.md | — |
| Очередь мешинга | MVP | 15-meshing-priority-queue-mvp.md | — |
| Node buffer | MVP | 20-gpu-node-buffer-mvp.md | — |
| Traversal | MVP | 21-gpu-simple-traversal-mvp.md | — |
| Occlusion culling | нет (MVP не имеет) | — | — |
| Temporal coherence | нет (MVP не имеет) | — | — |
| Mip-агрегация | MVP | 16-meshing-mipgen-mvp.md | — |
| GPU upload | MVP (не батчинг) | часть тикета 17 | — |
| Draw calls | MVP (обычные, не indirect) | часть тикета 27 | — |
| Dirty tracking | MVP | 26-render-dirty-tracking-mvp.md | — |
```

Обнови эту таблицу КАЖДЫЙ раз, когда применяешь любой `*-opt` тикет (см.
`P0-profiling-checkpoint.md`, критерий приёмки 4) — заполни столбец "Дата/повод перехода"
кратким обоснованием (например, "профилирование 2026-XX-XX показало contention на локе
кэша при холодном старте, см. PROFILING_RESULTS.md"), чтобы было видно не только ЧТО
изменилось, но и ПОЧЕМУ — это предотвращает ситуацию, когда будущая сессия видит opt-версию
в коде и не понимает, было ли это решение обосновано измерением или добавлено "на всякий
случай" в обход всего смысла MVP-first подхода.
```

### Шаг 2 — обязанность ведения (применяется ко ВСЕМ тикетам проекта, не только к этому)
Начиная с момента, когда `PROJECT_INDEX.md` создан этим тикетом, **каждый последующий тикет
(любой файл из диапазона 00-31, включая все его mvp/opt суффиксные варианты — например,
`08-storage-section-cache-mvp.md` И отдельно, если/когда применяется,
`08-storage-section-cache-opt.md` — а также сам `P0-profiling-checkpoint.md`, который не
входит в числовой диапазон, но обязан вести индекс наравне с остальными, в первую очередь
обновляя новую секцию "🌊 Статус MVP/opt волн", в любом порядке их фактического выполнения)
обязан завершаться обновлением `PROJECT_INDEX.md`** следующим образом — добавь этот же текст
как финальный пункт в критерии приёмки любого тикета, который будет выполняться ПОСЛЕ этого
(если тикет уже был выполнен ДО этого момента — обнови индекс за него ретроактивно, см.
требование 4 ниже):

1. Отметь тикет как `DONE` в таблице статуса, с краткой (1-2 строки) заметкой, если финальная
   реализация в чём-то содержательно отклонилась от того, что было прописано в тексте тикета
   (переименован метод, изменена сигнатура, добавлен незапланированный вспомогательный
   класс) — не дублируй Javadoc, только то, что важно для кого-то, кто НЕ читал этот тикет и
   хочет быстро понять, чего ожидать от кода.
2. Добавь/обнови одну строку на каждый новый публичный класс, созданный этим тикетом, в
   секции "Ключевые классы", в формате, аналогичном примерам ниже (стиль — как в приведённом
   выше `project-index` образце из Exceptional Vision: компактно, по существу, включая
   неочевидные "гочи" — то, что не видно из одной сигнатуры метода, но важно знать при
   использовании класса):
   ```
   - `SectionCache` — sharded concurrent section cache, 64 shards by default, bit-mixed
     hash (NOT naive modulo — see Javadoc for why). acquire()/release() reference-counted.
     Metrics reported via MetricsRegistry on every acquire (hit/miss).
   ```
3. Если тикет вводит или уточняет межмодульный контракт, оставленный предыдущим тикетом как
   "рабочее предположение" (класический случай — `resolveChildNodeId` в тикете 21,
   `NodeGeometryInfo`-подобная схема в тикете 23, обе явно помечены как "финализируется
   позже") — задокументируй финальную версию в секции "Межмодульные контракты, зафиксированные
   де-факто", даже если формально это работа другого тикета — здесь фиксируется РЕЗУЛЬТАТ,
   не важно, в рамках какого именно тикета он появился.
4. Если этот тикет 32 выполняется НЕ первым (то есть некоторые из тикетов 00-31 уже были
   выполнены ДО него) — исполнитель этого тикета должен пройтись по уже существующему коду
   (через `view` по реальной структуре директорий) и заполнить `PROJECT_INDEX.md` ретроактивно
   для всего, что уже сделано, а не оставлять эти секции пустыми только потому, что
   формальный призыв "обновляй по ходу" появился позже фактического выполнения тех тикетов.

## Требования к реализации
1. `PROJECT_INDEX.md` — plain markdown, без вложенных поддиректорий (весь файл — один
   документ, не набор файлов) — простота лукапа важнее structural elegance здесь; если файл
   станет неудобно большим (полностью реализованный проект, все 32 тикета учтены) — не
   разбивай его без явного отдельного решения, компактность через дисциплину формулировок
   ("одна строка на класс", не абзац), не через модуляризацию самого индекса.
2. Не дублируй содержимое Javadoc или самих тикетов дословно — `PROJECT_INDEX.md` это
   компас, не архив; если для полного понимания нужен весь Javadoc класса — читатель откроет
   сам файл, это ожидаемо и нормально, индекс лишь подсказывает, ГДЕ смотреть и стоит ли
   вообще смотреть для конкретной задачи.
3. Никакого пересказа истории решений/причин багов сюда — это explicitly НЕ прогресс-лог
   (если EV когда-либо заведёт свой аналог `PROGRESS.md` из Exceptional Vision — это
   отдельный, не входящий в объём этого тикета артефакт; `PROJECT_INDEX.md` — только текущее
   состояние структуры, не путь к нему).
4. Финальный пункт критериев приёмки любого другого тикета (00-31) с этого момента должен
   явно включать "обновить `PROJECT_INDEX.md` согласно тикету 32" — сформулируй этот пункт
   в самом `PROJECT_INDEX.md` (в его собственном заголовке, как сделано в шаблоне Шага 1 —
   "Читай это ПЕРЕД тем, как обходить файлы вручную") как самодостаточную инструкцию, не
   полагаясь на то, что каждый отдельный будущий тикет обязательно процитирует этот тикет
   явно (они физически не могут, если выполняются в изоляции без доступа к этому документу
   в контексте своей сессии) — то есть сам факт существования и заметности
   `PROJECT_INDEX.md` в корне репозитория должен быть достаточным сигналом любому
   добросовестно работающему агенту вести его дальше, даже если конкретный текст тикета,
   который агент читает, не упоминает тикет 32 напрямую.

## Критерии приёмки
1. `PROJECT_INDEX.md` создан в корне репозитория.
2. Если на момент выполнения этого тикета уже существует какой-либо реальный код (тикеты
   00-31 частично выполнены до этого момента) — все существующие модули/пакеты/публичные
   классы отражены в файле согласно формату из Шага 1 (ретроактивное заполнение, см.
   требование 4 в Шаге 2).
3. Файл читаем и полезен как самостоятельный документ — тест на это: если убрать доступ ко
   всем остальным файлам проекта, кроме `PROJECT_INDEX.md`, можно ли по нему понять, что уже
   есть, а чего нет, и где физически искать нужный класс — если нет, секции недостаточно
   конкретны, дополни.
4. Секция "Чего пока не существует" явно перечисляет хотя бы то, что достоверно известно на
   момент выполнения этого тикета (например, если тестовая инфраструктура ещё не создана —
   отметь это явно, аналогично тому, как это было полезно сделано в независимой более ранней
   реализации: "No unit tests, no sourceSets.test" — прямая, недвусмысленная формулировка
   экономит время следующей сессии на бесплодный поиск).
